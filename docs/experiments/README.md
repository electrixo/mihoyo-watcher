# 前瞻窗口 cron 对照实验（已归档）

> **实验已结束，本目录仅作历史留档。** 结论：拆分写法 day1 两条都派发、day2 两条都被吞，
> 派发本身随机，写法不是决定性因素。现行方案为「密打 + 分槽去重」，见 [`../slots-dispatch.md`](../slots-dispatch.md)。
> **不要再把这里的 yml 覆盖到 `.github/workflows/`。**

## 要回答的问题

同一 workflow 里，前瞻窗口的 22:07 / 22:37 两个触发，为什么 22:37 从来没派出来过？

- 是**写在一起**（`7,37 14 * * 3,5,6`）会被合并/丢弃？
- 还是**分开写**（两条独立 cron）也一样？

## 两版文件

| 文件 | 前瞻 cron | 说明 |
|---|---|---|
| `watch-split.yml` | `7 14` + `37 14` | 拆分写法（现网正在跑） |
| `watch-merged.yml` | `7,37 14` | 合并写法 |

两份都是完整可用的 workflow，除前瞻 cron 与对应的 `if` / `--codes-only` 判断外完全相同。

**用法**：把要测的那份覆盖到 `.github/workflows/watch.yml`，提交即可。不要两份同时留在 `.github/workflows/` 下。

## 关键约束

一个 workflow 同一时间只能有一份 `schedule`。所以两版**不能同时生效**，只能分时段切换。

如果以后想同时对照，可以另建一个独立 workflow 文件（例如 `probe.yml`），只保留：

```yaml
on:
  schedule:
    - cron: "7,37 14 * * 3,5,6"
```

里面只做一件事：把 `github.event.schedule` 写进 Job Summary，**不抓码、不推送、不提交状态**。这样两套调度互不干扰，同一天就能拿到两组数据。

## 怎么判定

每个前瞻日（周三 / 周五 / 周六）看一次运行列表：

| 观察结果 | 结论 |
|---|---|
| 两条运行，`schedule=` 分别是 `7 14...` 和 `37 14...` | 拆分有效 |
| 只有一条 | 与合并写法表现相同，说明瓶颈不是写法 |
| 合并版某天出现两条 | 说明拆分写法反而更容易被吞 |

判定以 **3 个前瞻日** 为准，单日样本不作数（日级积压会让某天整体晚 3–5 小时）。

## 记录
