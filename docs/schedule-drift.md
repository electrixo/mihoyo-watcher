# GitHub Actions 定时偏移：它就是这个脾气

我们每天要收日报、要抓码，但 GitHub 的定时器从来不是闹钟。

这张表是给它摸脉——每次触发到底几点跑、跑没跑。结论放前面：**会晚 4~12 小时，偶尔吞掉一次前瞻触发，但每天该有的都有，兜底也都在。** 所以不用跟它较劲，记下来就行。

> 口径：实际时刻取运行的创建时间。「创建 → 开跑」的排队延迟恒为 0，差值全来自调度器决定什么时候创建这一步。

## 2. 看下来就三件事

| 时段 | 样本 | 最快 | 中位 | 最慢 | 波动 |
|---|---|---|---|---|---|
| 14:10 签到兜底 | 8 | 8h17m | **9h25m** | 11h46m | 3.5h |
| 22:07 / 22:37 前瞻 | 5 | 6h20m | **7h41m** | 8h55m | 2.6h |
| 02:45 抓码 | 7 | 4h51m | **6h10m** | 9h20m | 4.5h |
| 04:15 日报 | 7 | 4h07m | **5h32m** | 8h34m | 4.5h |

1. **每个时段的“起床时间”不一样**：14:10 那轮最慢，中位 9 小时出头；02:45 / 04:15 那对最利索，5~6 小时。
2. **最快 4h07m，最慢 11h46m**，中间隔着 7 小时 39 分。
3. **快慢基本按天成组**：11-21 / 11-22 那两晚都在 4~5 小时，11-23 起整体升到 7~9 小时。所以"昨天快"不代表今天快，但同一天内的几个触发往往接近。

31 个定时事件，兑现 28 个，历史丢 3 个（都是合并写法时期的第二次前瞻）。

## 3. 三次“没派出来”，指向同一个原因

前瞻窗口在 22:07 和 22:37 各来一次，11-18 / 11-20 / 11-21 三天里，每次都只来了 22:07 那条，22:37 一次没派出来。

对照一下：18:45 和 20:15 相隔 **90 分钟**，两个每天都能派出来；前瞻那对只隔 **30 分钟**，第二个三天全丢。
看起来瓶颈是**间隔太密**——前一个还在积压里，后一个到了就被合并/顶掉，跟逗号写法无关。

11-24 已经把 `7,37 14 * * 3,5,6` 拆成两条独立 cron。**11-25 首个样本：两条都来了**——22:07 → 07:02（8h55m）、22:37 → 07:16（8h39m），Job Summary 分别显示 `7 14 * * 3,5,6` 和 `37 14 * * 3,5,6`。

这说明之前那三次被吞，问题出在**合并写法的逗号列表**，拆成两条独立 cron 后第二次触发能正常派发。

还要再看 11-27 周五、11-28 周六 两次，确认不是偶然。如果都稳定两条，就保留拆分写法。

这不影响任何功能：两次跑的是同一条 `--codes-only` 命令，加上 02:45 那趟，本来就有覆盖。

## 4. 怎么和它相处

1. **提前量按中位数给**，别指望对齐到分钟。对齐了也是运气，不是本事。
2. **三条兜底互相独立**：02:45 只抓码、04:15 日报、14:10 签到补签。任何一条晚到、甚至没来，都不影响另外两条。
3. **能收到就算赢**。日报晚几小时不影响兑换码的有效期，签到补签本来就是兜底用的。
4. **真要准点**（比如抢首码），就别用 GitHub 的闹钟：国内常开云主机上挂个系统 cron，到点调一次 `workflow_dispatch`，秒级必达。一个月几块钱，不折腾也行——现在的“能收到”已经够用了。

## 5. 这张表怎么维护

- 新增一次定时运行，就往第 1 节加一行。
- 改动 cron，另起一段，不覆盖历史。
- 写它的目的很简单：**哪天它变卦了，我们能一眼看出是从哪一天开始变的。**

| 轮次 | 触发 BJT | 目标到达 | 预计到达窗口 |
|---|---|---|---|

- **签到兜底**：原 14:10 触发，到达 22:27–次日 01:56，有 3 次跨天（跨天就会签成次日）。
  新触发 11:05，到达 19:22–22:51，全部落在当天。
- 本节之后的数据按新触发统计，历史样本不混算。

## 7. 2026-11-27 起：密打 + 分槽（放弃反推）

探针与 24 小时数据证实：问题不是"延迟大"，而是"派发本身随机且极少"——
19 个定时触发只兑现 1 次；最简 workflow（单 cron/单 job/无状态提交）同样不被派发。
所以反推触发时刻的前提不成立，改为：

| 项 | 值 |
|---|---|
| cron | `7,37 * * * *`（48 点/天，被丢弃的点不产生请求） |
| 实际兑现 | 约 4~5 次/天 |
| 推送去重 | 早报 00–12 / 午报 12–18 / 晚报 18–24，每槽每天最多一条日报 |
| 新码 | 不受槽限制，随时推 |

- 派发发生时是准的（探针 +28m），所以密打只花钱不浪费：每槽期望约 1 次兑现
- 同账号旧哨兵 `mihoyo-code-watch` 长期使用同一方案（`7,37 1-11 * * *` + `push_slots` 去重）
- 本节之前的历史样本按旧 cron 统计；本节之后的运行按新 cron 统计，不混算
