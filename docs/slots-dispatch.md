# 设计稿：放弃"反推触发"，改用「密集打点 + 分槽去重」

> 交接给执行 agent。先讲清楚为什么推翻之前的方案（证据链），再给新设计。
> 改动分两块：**cron 换成密集打点** + **应用层加推送槽（push slots）**。
> 业务逻辑（抓取、识别、签到）不动。
>
> 撰写时间：2026-11-27
> **状态：已于 2026-11-27 在本地实现**（watch.yml 单条密打、watch_mihoyo.py 三槽去重、
> 91 个离线测试通过），尚未推送。本文件保留为设计依据。

## 1. 为什么推翻「按到达时刻反推触发」（证据链）

之前的方案假设：**派发必然发生，只是延迟 4~12 小时**，所以把触发提前就能保证落点。
这个前提被三天实验否定了：

| # | 证据 | 时间 |
|---|---|---|
| 1 | 28 个样本：偏移 4h07–11h46，且 22:37 触发点 4 次被吞 | 11-18 ~ 11-26 |
| 2 | 拆分实验：day1 两条前瞻都派发，day2 两条都没派发 | 11-26 早 / 11-27 早 |
| 3 | 探针（单 cron / 单 job / 无状态提交）：hourly 13 个触发只兑现 1 个，daily 首触发未兑现 | 11-26 晚 ~ 11-27 |
| 4 | 24 小时内约 19 个定时触发，只创建 1 条运行（派发率约 2%） | 11-26 全天 |
| 5 | **原哨兵仓库的注释（同账号，实测更久）**：`实测：配 48 次/天时，一天真正只跑了 4 次左右`、`实测少打点时会被整轮丢弃（11-17 那天的 4 个点全军覆没）` | 长期 |

第 5 条是决定性的：**同一个账号早就在另一个仓库里实测过同样的现象**，并且已经给出了
被长期使用验证过的解法——密集打点 + 应用层去重（`push_slots`）。

### 补充观察（同样重要）

- **派发发生时是准的**：探针 19:07 触发 → 19:35 创建（+28m），与另一个项目 +4~28 分一致。
  所以排队不是问题，**问题是派发几乎不发生、且落在哪个触发点不可预测**。
- 派发量按天波动：11-25/26 每天兑现 4~5 次，11-26 晚~11-27 只兑现 1 次。

## 2. 设计原则

1. **不赌派发时刻**：调度器一天只兑现少数几次、时刻近乎随机，任何"单点触发 + 反推"
   都是脆弱的。
2. **用打点密度换覆盖概率**：public 仓库 Actions 不计费；被丢弃的触发点不产生任何
   请求和运行，密打的真实成本 = 兑现次数 × 每轮请求（约 4 次/天 × 20 请求），与现在持平。
3. **正确性由应用层保证**：重复运行必须无副作用——推送靠「分槽去重」，签到靠幂等，
   抓码靠 code 去重（后两者已有）。
4. **所有轮次合一**：不再区分"抓码轮/日报轮/签到轮"，一个 workflow、一条密打 cron，
   每次兑现都跑完整任务，推送内容由槽位规则决定。

## 3. cron 设计

```yaml
on:
  schedule:
    - cron: "7,37 * * * *"      # 每 30 分钟一个点（GitHub 允许的最短间隔为 5 分钟）
  workflow_dispatch:             # 保留 dry_run / test_push
    ...
```

- 每天 48 个触发点；按实测兑现率（约 4~5 次/天），实际运行 4~5 次；
- 保留 `:07/:37` 的分钟位置（避开整点高峰）；
- 原来的 5 条 cron（02:45 / 08:10 / 11:05 / 22:07 / 22:37）全部废弃，
  抓码、日报、签到、前瞻的职责由「每次兑现都跑完整流程」承接。

## 4. 推送槽（push slots）：应用层唯一的新逻辑

### 4.1 资讯发布背景

米游社资讯发布集中在两个窗口：**12:00（约 53%）和 18:00（约 24%）**。
凌晨到上午只有零散发布。

### 4.2 三个槽

| 槽 | 到达窗口（BJT） | 对应发布 | 内容 |
|---|---|---|---|
| `morning` | 00:00 – 11:59 | 昨天下午/晚间的发布 | 「昨天的报」 |
| `noon` | 12:00 – 17:59 | 当天 12:00 的发布（53%） | 「午报」 |
| `evening` | 18:00 – 23:59 | 当天 18:00 的发布（24%） | 「晚报」 |

### 4.3 规则

1. 每次兑现运行时，先算 `now` 属于哪个槽（北京时间）；
2. 查状态：该槽**今天**是否已推送过；
3. 已推 → 只跑抓取和登记（静默，不推送）；
4. 未推 → 正常按「有新内容才推」的规则执行；推送成功后记 `last_push[slot] = today`；
5. 码的推送**不走槽**：新码随时推（沿用现有 code 去重）；
6. 签到**不走槽**：幂等，照常执行（未启用时跳过）。

### 4.4 状态结构（`state/seen_news.json` 扩展）

```json
{
  "posts":   { ... 现有 ... },
  "codes":   { ... 现有 ... },
  "slots":   { "morning": "2026-11-27", "noon": "", "evening": "" }
}
```

`slots` 每天清零（进入新的一天后，日期不匹配即视为未推）。
原子写、无变化不写，沿用现有 `save_state` 逻辑。

### 4.5 边界情况

- **槽内无兑现**：某槽当天一次兑现都没有（概率低——兑现散布全天，每槽期望约 1 次，
  但会偶发）。后果是该槽的资讯并入下一槽的日报，不丢数据，只是晚到；
- **槽已推之后又出现新资讯**：不登记为已读，保留到下一槽再推（避免静默吞掉）；
  下一槽的日报会带上这些「上一槽遗留 + 本槽新增」的内容；
- **兑现落在槽边界附近**：按脚本运行时刻（北京时间）判断槽，12:00 前后几分钟的
  归属误差可接受；
- **重复推送防护**：同槽同日只推一条；不同槽内容可能重叠（如 noon 与 evening 都含
  同一条置顶公告）——由现有的 post 去重兜底：已见过的 post 不再算"新内容"，
  无新内容就不推，天然不重复。

## 5. 每次兑现的运行流程（改后）

```
cron 兑现（每天约 4~5 次，时刻随机）
  → 跑单元测试（保持现状）
  → 抓资讯（3 游戏 × 3 类型）+ 搜索抓码
  → 签到（幂等；未启用则跳过）
  → 判定当前槽；查 slots 状态
      ├─ 槽已推 → 只登记新内容到状态，不推送
      └─ 槽未推 → 有新内容则推送该槽日报；无新内容只登记
  → 新码随时推送（现有逻辑）
  → 保存状态、提交（仅当状态有变化）
```

## 6. 预期效果

| | 旧方案（4 条 cron + 反推） | 新方案（密打 + 三槽） |
|---|---|---|
| 日报到达 | 依赖单点兑现，会被整轮丢弃 | 每槽期望 1 次兑现，丢失是「延后到下一槽」而非「没有」 |
| 覆盖 12:00 发布 | 1/7 | noon 槽存在即覆盖（前提是槽内有兑现） |
| 覆盖 18:00 发布 | 不可能（无晚间抓取） | evening 槽覆盖 |
| 重复推送 | 靠 post 去重 | post 去重 + 槽位门，双保险 |
| 单日请求量 | ~5 轮 × 20 | 相同（兑现次数不变） |
| 运行记录 | 3~5 条/天 | 4~5 条/天（被丢弃的 cron 点不留记录） |

## 7. 验收方法

1. 跑全部离线测试（新增槽位逻辑的单测：同槽同日不推、跨天清零、槽边界归属）；
2. 推上去后观察 2~3 天：
   - Actions 列表每天应有 3~6 条运行（兑现次数）；
   - 每条运行的 Job Summary 应标注它落在哪个槽、推没推；
   - pushplus 每天应收到 ≤3 条日报 + 0~N 条新码；
3. 特别核对：当天 12:00 发布的资讯是否出现在 `noon` 或 `evening` 槽的日报里。

---

## 8. 边界：这些不要动

| 不要动 | 原因 |
|---|---|
| 抓取 / 识别 / 签到逻辑 | 本次只改调度与推送时机 |
| `mihoyo_http.py` 的请求节流 | 密打不增加实际请求量（兑现次数不变） |
| 签到的 `CHECKIN_ENABLED` 开关 | 与本任务无关 |
| 状态文件结构里已有的 `posts` / `codes` | 只新增 `slots` 键，旧数据兼容（缺省视为未推） |

## 9. 已知取舍

- 早上那段不再保证有日报——`morning` 槽兑现时若无新内容就静默；用户已接受
  「早上看昨天的报，或干脆没有」；
- 调度器派发量若某天骤降为 0（如 11-26 晚），当天所有槽都缺失——这是 GitHub 侧的
  底线，无法绕过；真要 100% 必达只能上外部触发（云主机 + `workflow_dispatch`），
  属于另一个任务。
