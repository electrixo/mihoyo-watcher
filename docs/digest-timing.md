# 任务：把日报触发后移，让它覆盖当天 12:00 的资讯

> 交接给执行 agent。这是一份**可直接照做**的改动说明：先讲清楚现在出了什么问题，
> 再给具体改法、预期效果和验收方法。改动只涉及 cron 与对应配置，不改业务逻辑。
>
> 仓库：`electrixo/miyoshe-watcher`（公开，零第三方依赖，GitHub Actions 运行）
> 撰写时间：2026-11-26

---

## 1. 项目背景（30 秒）

一个跑在 GitHub Actions 上的米游社福利监测工具，每天做三件事：

| 轮次 | 做什么 |
|---|---|
| 抓码 | 搜索「兑换码/前瞻/礼包」等关键词，识别并推送新兑换码 |
| 日报 | 抓三款游戏（原神 / 星穹铁道 / 绝区零）的公告、活动、资讯 + 码，合成一条日报 |
| 签到 | 可选，默认关闭（`CHECKIN_ENABLED` 未设置时不运行） |

关键点：**抓取时间由 GitHub 的 cron 决定，但 GitHub 的定时器有数小时延迟**，
真正到达时间 = 触发时刻 + 延迟。这个延迟不可控，是下文问题的根源。

## 3. 问题：日报几乎总是错过当天 12:00 的发布

### 3.1 现象

米游社的资讯发布高度集中在整点（星铁 17 条样本）：

| 发布时段 | 占比 |
|---|---|
| 12:00 | 53% |
| 18:00 | 24% |
| 13:00 / 14:00 / 19:00 | 少量 |

而我们的日报到达中位数是 **09:47**，**整个到达窗口 08:22–12:49 压在 12:00 之前**。

### 3.2 后果

- **12:00 发布的 53% 资讯，当天抓不到**，要等第二天 11 点左右的日报才带上；
- 18:00 发布的 24% 同理，而且**当天没有任何一轮抓资讯**（14:10 那轮只签到）；
- 也就是说，资讯对用户是「晚一天到」，不是「当天到」。

### 3.3 证据

- 11-24 日报 12:49 到 → 带上了当天 12:00 的资讯（唯一的成功案例）；
- 11-25 日报 11:33 到 → 差 27 分钟，没带上；
- 11-26 日报 10:58 到 → 差 1 小时，没带上。

---

## 4. 原因

### 4.1 公式

```
到达时刻 = 触发时刻 + 延迟（4h07 ~ 8h34，中位 5h32）
```

触发时刻是我们唯一能控制的变量，延迟是 GitHub 调度器的黑盒，**方差 4 个半小时**。

### 4.2 为什么 04:15 一定不行

要让日报**保证**覆盖 12:00，触发必须满足：

```
触发 + 最小延迟(4h07) > 12:00
→ 触发 > 07:53 BJT
```

现在的 04:15 差得很远，所以窗口整体压在 12:00 前。

### 4.3 这是概率问题，不是对时问题

延迟方差太大，任何固定触发都只能提高「越过 12:00」的概率，不能保证。
如果要 100% 准点，只能绕开 GitHub 调度器、用外部定时器调 `workflow_dispatch`
（本任务不做）。

## 5. 方案对比（按实测 7 个样本回算）

| 触发（BJT） | 到达窗口 | 中位到达 | 越过 12:00 比例 | 最晚到达 |
|---|---|---|---|---|
| 04:15（现在） | 08:22 – 12:49 | 09:47 | 1/7（14%） | 12:49 |
| 06:30 | 10:37 – 15:04 | 12:02 | 4/7（57%） | 15:04 |
| **07:30（选定）** | **11:37 – 16:04** | **13:02** | **6/7（86%）** | 16:04 |
| 08:00 | 12:07 – 16:34 | 13:32 | 7/7（100%） | 16:34 |

## 6. 为什么选 07:30

- 86% 的覆盖率，代价可接受；
- 中位下午 1 点到，最晚 4 点，仍在「当天」；
- 08:00 虽然 100%，但要牺牲到最晚 4:34，且样本只有 7 个，先留作后备。

换算 UTC：**07:30 BJT = `30 23`（前一天 23:30 UTC）**。

## 7. 具体改动（共 10 处，都是把 `04:15 / 15 20` 改成 `07:30 / 30 23`）

### 7.1 `.github/workflows/watch.yml`（4 处）

**① 头部说明**
```diff
-#   04:15 BJT 触发（UTC 20:15 前一天）→ 完整日报（资讯+码）+ 签到
+#   07:30 BJT 触发（UTC 23:30 前一天）→ 完整日报（资讯+码）+ 签到
```

**② cron 声明**
```diff
-    - cron: "15 20 * * *"         # BJT 04:15 触发 → 完整日报 + 签到
+    - cron: "30 23 * * *"         # BJT 07:30 触发 → 完整日报 + 签到
```

**③ `watch` job 的 `if`**
```diff
-      github.event.schedule == '15 20 * * *' ||
+      github.event.schedule == '30 23 * * *' ||
```

**④ `checkin` job 的 `if`**
```diff
-        github.event.schedule == '15 20 * * *' ||
+        github.event.schedule == '30 23 * * *' ||
```

> `--codes-only` 分支不用改：它只列举了 02:45 和两条前瞻 cron，日报走 `else`。

### 7.2 `tests/test_workflow.py`（2 处）

**⑤ 设计意图注释**
```diff
-#   DIGEST         04:15 BJT → 完整日报 + 签到
+#   DIGEST         07:30 BJT → 完整日报 + 签到
```

**⑥ 常量**
```diff
-DIGEST = "15 20 * * *"
+DIGEST = "30 23 * * *"
```
其余断言都引用这个常量，会自动跟随，不用逐条改。

### 7.3 `README.md`（2 处）

**⑦ 定时表**
```diff
-| 04:15 | `15 20 * * *` | 完整日报 + 签到 | 有新资讯/新码 → 日报；签到失败 → 告警 |
+| 07:30 | `30 23 * * *` | 完整日报 + 签到 | 有新资讯/新码 → 日报；签到失败 → 告警 |
```

**⑧ 限制说明**
```diff
-- **04:15 是当天唯一的资讯抓取**：这一轮被丢弃时，当天可能没有资讯日报，次日会补上（不丢数据，只延后）
+- **07:30 是当天唯一的资讯抓取**（到达约 11:37–16:04）：这一轮被丢弃时，当天可能没有资讯日报，次日会补上（不丢数据，只延后）
```

### 7.4 `docs/HANDOFF.md`（4 处）

- 第 14 行职责拆分概述：`04:15 完整日报 + 签到` → `07:30 完整日报 + 签到`
- 第 144 行定时表：同上

## 9. 验收方法

1. **跑测试**：`python -m unittest tests.test_watch_mihoyo tests.test_mihoyo_codes tests.test_mihoyo_comments tests.test_workflow`，应全绿（当前 89 个）。
2. **推上去后确认 cron 生效**：下一次日报运行的 Job Summary 第一行应显示
   `触发 event=schedule schedule=30 23 * * *`。
3. **观察 3 天**：看运行列表里日报到达时间是否落在 11:37–16:04，以及日报正文是否带上了
   当天 12:00 发布的帖子。
4. 第一天如果有一次「没出现」，先别下结论——改 cron 后 GitHub 偶尔有一次过渡期丢失。

---

## 10. 边界：这些不要动

| 不要动 | 原因 |
|---|---|
| 前瞻 cron `7 14` / `37 14`（拆分写法） | 正在做对照实验，改动会污染样本 |
| 签到逻辑与 `CHECKIN_ENABLED` 开关 | 签到当前未启用，改动无关 |
| 02:45 抓码轮、14:10 签到兜底 | 各有职责，不在本次范围 |
| 抓码识别逻辑 `mihoyo_codes.py` | 与时间窗无关 |
| 推送模板 / 状态文件结构 | 与时间窗无关 |

**另外要清楚**：这次改动只解决 12:00 那 53%；18:00 发布的 24% 仍然只能次日见，
因为当天 18:00 之后没有任何一轮抓资讯。要覆盖它得再加一轮晚间抓取，属于后续独立任务。
